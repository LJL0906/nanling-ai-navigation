# 菜单接口与管理说明

## 已完成的闭环

```text
/admin/menus/ 管理页
  → Bearer 鉴权的 GET / PUT /api/admin/menus
  → 校验完整菜单与 revision
  → MySQL nav_menus 事务保存
  → GET /api/menus 与前台组件共用读取层
  → 侧栏、顶部导航、用户菜单、通知和底部设置更新
```

前台组件在服务端直接调用公共菜单读取层，不绕 HTTP 请求本站接口；公开 API 与页面使用同一数据源。MySQL 模式没有菜单快照缓存，也不会在数据库失败时偷偷回退静态种子。保存后下一次页面请求或刷新即可读取新菜单；已打开的页面不会自动推送刷新。

本轮是**菜单**管理闭环，不包括站点/分类的运营增删改和 `nav_settings` 配置管理。品牌文案、搜索词、首页筛选规则、精选目录页等非菜单内容仍按原有实现读取；修改顶部某个资源菜单，不会同步改写精选目录卡片。

## 使用方式

1. 确认本地 `.env` 为 `NAV_STORAGE=mysql`，数据库已有菜单表和初始数据。
2. 启动或重启应用，进入 `/admin/`，点击“进入菜单管理”，也可直接访问 `/admin/menus/`。
3. 使用服务端配置的 `ADMIN_TOKEN` 验证。不要把数据库密码当管理令牌，不要发送令牌到聊天或写入 URL。
4. 选择菜单修改字段，或新增菜单。新菜单默认隐藏，核对链接后勾选“启用”。
5. “应用到本页草稿”只修改页面内存；“保存全部”才会一次提交新增、修改、排序、显隐和删除。
6. 保存成功后刷新前台核对。删除分组会同时删除其子菜单，页面会先要求确认。

令牌、草稿只保存在当前页面内存，退出、刷新、离开页面或 BFCache 回访后需要重新验证。页面不将它们写入 localStorage、sessionStorage 或查询参数。

后台修改的是**站点默认排序**，不清除访客既有的个人排序；保留首页固定首位的原有浏览器交互。个人排序键继续兼容已有分类路径。菜单的启用/隐藏始终以服务器结果为准。

## 接口

### GET /api/menus

公开接口，返回当前可见的扁平菜单列表，父子关系通过 `parentId` 表达。禁用父项的子菜单也不会返回。

```json
{ "data": [
  { "id": "menu:example", "parentId": null, "location": "topbar", "kind": "link",
    "label": "示例入口", "href": "/search/", "icon": "lucide:search", "sortOrder": 10,
    "enabled": true, "payload": {} }
] }
```

### GET /api/admin/menus

需要 `Authorization: Bearer <ADMIN_TOKEN>`。返回完整列表（包括隐藏项）、内容版本和可写状态。

```json
{ "data": { "menus": [], "revision": "64位SHA256内容版本", "writable": true } }
```

上述空数组仅表示响应结构，不是可提交的有效菜单数据。

### PUT /api/admin/menus

同样需要 Bearer 头，Content-Type 必须为 `application/json`。

```json
{ "menus": ["此处提交完整菜单对象列表"], "revision": "上一次读取到的64位版本" }
```

成功响应与管理查询相同。缺少/无效令牌返回 401，未配置管理令牌返回 503；过期版本或写锁竞争返回 409；非法字段返回 400；错误媒体类型返回 415；超过 512 KiB 返回 413。不支持的方法返回 405（框架可能先拒绝跨源不安全请求）。

整批替换是有版本保护的事务操作：管理页必须从服务端读取后再修改；不要只发送单条菜单，否则未包含的菜单会被视为删除。409 时必须重新加载，不能自动使用新版本重试旧草稿。

## 字段和约束

- `id`：稳定唯一标识，最长 191 字符，允许字母数字及 `: / _ . -`；页面自动生成新 ID。
- `location`：`sidebar`、`sidebar-footer`、`topbar`、`topbar-actions`。
- `kind`：`link`、`category`、`group`、`resource`。
- `parentId`：根项为 null；只支持一层子菜单，父项必须是同区域根分组。
- `group`：仅在顶部区域，必须是无链接的根项。
- `resource`：仅在顶部导航的分组下。
- `label`：非空名称；`href` 仅支持 `/` 开头的站内路径或无账号密码的 HTTP(S) 链接，锚点使用 `/#anchor`。
- `icon`：null 或已安装的 `lucide:` 图标；服务端按白名单渲染，保存后不需要重新构建图标。
- `sortOrder`：0–1000000 的整数；同位置和同父节点下按此值排序，值相同时用 ID 稳定排序。
- `enabled`：布尔值；禁用分组会隐藏全部子菜单。
- `payload`：JSON 对象，可保存描述、打开方式和已有分类关联信息。禁止原型污染键，限制嵌套及大小；`target` 只支持 `_blank` / `_self`，新窗口链接强制 `noopener noreferrer`。
- 分类菜单保留与现有分类匹配的首页锚点和分类路径，不能把普通外链当分类锚点处理。
- 菜单总数 1–500；单项 payload 不超过 16000 字符；请求流按 UTF-8 字节限制为 512 KiB，不只依赖 Content-Length。

## 写入与故障边界

- API 先鉴权再读取提交正文和连接数据库，不接受 URL/Cookie 中的管理凭据，不开放跨源写入。
- 菜单表必须是 InnoDB；与初始化工具共用命名锁。
- 在同一事务内锁定现有行、检查版本、验证分类关联、参数化写入并全量回读。
- 分组移动/删除过程中只在事务内暂时解除父引用，不关闭外键校验；失败回滚。
- 提交后的下一次读取使用数据库内容，不覆盖静态源文件。
- 种子模式提供相同公开菜单结构，但管理接口只读，不能保存。
- `nav_settings` 不会随着菜单保存被覆盖。

后台投入使用后，菜单表与静态种子不同是正常现象。`db:sync-menus` 和 `db:verify-static` 仍用于首次初始化/种子一致性核对，不能作为强制恢复或覆盖运营菜单的命令。
