二、当前最重要的问题

1. 统一数据和展示数据没有衔接层
   现在页面类型是：
   interface Site {
   name: string;
   slug: string;
   url: string;
   desc: string;
   icon: string | null;
   color: string;
   mono?: string;
   preview?: 'light' | 'blue' | 'dark';
   }
   而统一数据字段是：
   description
   category
   sourceCategories
   verification
   sources
   alternateUrls
   classification
   字段不一致：
   desc          vs description
   icon: string  vs icon: object | null
   category 内嵌  vs category ID 关联
   所以不能直接替换 JSON，需要增加一层：
   统一原始数据
   ↓
   数据适配 / 清洗 / 筛选 / 排序
   ↓
   页面展示模型
   建议不要让页面组件直接依赖原始数据格式。
2. sourceCategories 不能直接作为二级 Tab
   例如 AI 类下面现在可能有：
   AI图像工具
   常用AI图像工具
   AI写作工具
   AI智能体
   AI图片插画生成
   AI图片背景移除
   AI商品图生成
   AI表格数据处理
   AI副业工具
   ...
   这些字段存在几个问题：

- 命名不统一
- 粒度不一致
- 有重复语义
- 有些是功能分类，有些是场景标签
- 有些来自不同数据源，不能直接展示给用户
- 单个站点可能挂多个来源分类
  因此，二级 Tab 需要单独建立：
  展示用 Tab
  而不能直接拿原始分类名称作为 UI。

3. 当前只有“分类”，还没有“分类下的内容组织”
   理想闭环应当是：
   一级分类
   ↓
   二级 Tab
   ↓
   卡片列表
   ↓
   站点详情 / 外部访问
   ↓
   收藏、历史、反馈、数据质量回流
   现在只有：
   一级分类
   ↓
   卡片列表
   ↓
   外部访问

  四、一级分类、二级 Tab、卡片的完整逻辑

1. 一级分类逻辑
   一级分类负责：

- 顶部或侧边主导航
- SEO 分类页
- 分类级标题与描述
- 分类级站点聚合
- 分类级二级 Tab 容器
  数据来源：
  分类配置 + 站点 categorySlug
  排序建议：
  显式 order
  ↓
  没有 order 时按数据生成顺序
  ↓
  不要按名称自动排序
  原因是导航站的顺序本身带有运营意图。

2. 二级 Tab 逻辑
   二级 Tab 建议分成三种类型。
   固定 Tab
   每个分类默认存在：
   全部
   用于展示该分类下全部站点。
   运营 Tab
   例如 AI：
   全部
   AI 对话
   AI 写作
   AI 绘图
   AI 视频
   AI 音频
   AI 编程
   AI 办公
   AI 搜索
   AI 智能体
   这些是用户真正能理解的业务分类。
   动态标签
   不建议第一阶段直接把所有 tags 做成 Tab。
   可以把它们作为：
   筛选条件
   例如：
   免费
   中文
   无需注册
   开源
   国内可用
   支持 API
   推荐最终 UI：
   一级分类
   ├── 二级业务 Tab
   └── 可选筛选项
   不要把“分类”和“标签”混成同一层。
3. 站点归属规则
   每个站点建议具备：
   categorySlug: string;
   tabSlugs: string[];
   tags: string[];
   例如：
   {
   "name": "ChatGPT",
   "categorySlug": "ai",
   "tabSlugs": ["chat", "writing", "office"],
   "tags": ["大模型", "中文", "AI助手"]
   }
   站点可以属于：
   一个一级分类
   多个二级 Tab
   多个标签
   但要约束：
   一级分类只能有一个
   二级 Tab 可以多个
   标签可以多个
   这样既保证主分类清晰，也支持交叉展示。
4. Tab 筛选逻辑
   推荐初期采用 URL 查询参数：
   /ai/?tab=chat
   /ai/?tab=image
   /ai/?tab=writing
   原因：

- 不需要和现有 /[category]/[slug]/ 路由冲突
- 对现有站点详情页影响最小
- 前端切换逻辑简单
- 可以复制链接
- 可以保留浏览器前进后退状态
- 不会因为每个 Tab 生成大量独立 SEO 页面
  页面逻辑：
  const tab = Astro.url.searchParams.get('tab') ?? 'all';

const visibleSites =
  tab === 'all'
    ? category.sites
    : category.sites.filter((site) => site.tabSlugs.includes(tab));
Tab 点击：
点击二级 Tab
  ↓
更新 URL ?tab=xxx
  ↓
重新渲染 / 或客户端切换
  ↓
更新卡片数量
  ↓
更新空状态
  ↓
保留当前滚动位置
如果未来需要为某些核心 Tab 做 SEO，再单独增加：
/ai/chat/
/ai/image/
第一阶段不建议一开始就为全部 Tab 生成静态页面。

   图标 + 名称 + 描述
   标准卡片：
   图标

   收藏
   访问
   大卡片：
   预览图
   图标
   名称
   描述
   标签
   访问按钮
2. 卡片点击行为
   建议拆分为三个行为：
   点击名称
   进入站内详情页：
   /{category}/{site}/
   点击访问按钮
   新窗口访问外部 URL：
   site.url
   点击收藏
   写入本地存储：
   nav-favorites
   不要让整张卡片全部直接跳外站，否则用户很难进入详情页，也不利于后续扩展。
3. 收藏闭环
   当前项目已经有：
   /favorites/
   但需要和卡片真正打通。
   建议数据格式：
   [
   {
   "siteId": "site_0c372ce2acdc",
   "addedAt": "2026-09-07T12:00:00.000Z"
   }
   ]
   存储：
   localStorage["nav-favorites"]
   收藏逻辑：
   卡片点击收藏
   ↓
   校验 localStorage
   ↓
   按 siteId 去重
   ↓
   写入收藏时间
   ↓
   更新按钮状态
   ↓
   收藏页读取 siteId
   ↓
   从站点索引恢复完整卡片
   不要只存完整卡片数据，否则后续数据更新后容易出现旧数据。
4. 历史记录闭环
   访问外部站点时记录：
   {
   "siteId": "site_0c372ce2acdc",
   "visitedAt": "2026-09-07T12:00:00.000Z"
   }
   建议：
   最多保存 50 条
   同一站点重复访问只更新时间
   按 visitedAt 倒序
   记录入口：
   详情页访问官网
   卡片外链访问
   首页快捷卡片
   历史页再通过 siteId 从统一索引查回当前数据。

   外部数据源
   ↓

   ↓

   ↓

   ↓

   ↓
   页面展示
   ↓
   用户点击 / 收藏 / 历史
   ↓
   运营发现问题
   ↓
   回到数据配置修正
   具体建议：
   src/data/原始数据/
   src/data/导航数据.json
   src/data/导航配置.json
   src/lib/data.ts
   src/lib/types.ts
   职责划分：
   文件	职责
   导航数据.json	统一清洗后的站点总数据

七、二级 Tab 映射方案
不建议人工为 2400 个站点逐条维护 Tab。
建议采用：
规则自动映射 + 人工覆盖

1. 自动映射
   根据以下字段判断：
   sourceCategories
   name
   description
   tags
   classification.reason
   例如：
   包含“AI图像、绘图、图片生成”
   → image

包含“AI写作、文案、文本生成”
  → writing

包含“AI视频、视频生成、剪辑”
  → video

包含“AI聊天、对话、大模型助手”
  → chat
2. 人工覆盖
新增覆盖配置：
{
  "siteTabOverrides": {
    "chatgpt": ["chat", "writing", "office"],
    "midjourney": ["image"],
    "suno": ["audio"]
  }
}
人工配置优先级：
人工覆盖
  ↓
规则映射
  ↓
来源分类映射
  ↓
默认归入“其他”
这样可以避免每次重新导入数据后，所有人工调整都丢失。
3. 未归类数据处理
所有无法匹配二级 Tab 的站点不能被静默丢弃。
建议：
自动进入“其他”
并在开发校验中统计：
未归类站点数量
空描述数量
无效 URL 数量
缺失图标数量
重复 slug 数量
无对应一级分类数量

- HTML 体积变大
- 首屏渲染变慢
- DOM 节点数量增加
- 移动端筛选性能下降
- 搜索字段不够完整
  建议搜索索引字段增加：
  name
  aliases
  description
  domain
  category
  categoryName
  tabs
  tags
  sourceCategories
  搜索优先级：
  名称精确匹配

别名匹配
    >
域名匹配
    >
Tab 名称匹配
    >
标签匹配
    >
描述匹配
第一阶段可以继续使用静态客户端搜索，但建议：

- 初始只渲染前 60～100 条
- 输入后再显示更多
- 增加分类筛选
- 增加二级 Tab 筛选
- 增加空状态
- 处理 URL 参数和浏览器历史
  如果后续数据增长到 5000 条以上，再考虑构建静态搜索索引或服务端搜索。

    十一、当前最重要的几个决策
    我建议先确定以下方案：
    决策一：统一数据源
    采用：
    导航数据.json = 标准站点库
    导航展示配置.json = 分类、Tab、首页展示配置
    当前 sites.json 作为过渡兼容，不再继续扩充。
    决策二：二级 Tab 使用查询参数
    采用：
    /category/?tab=xxx
    而不是立即新增多级动态路由。
    决策三：站点支持多个 Tab
    采用：
    tabs: string[]
    primaryTab: string
    而不是强制一个站点只能属于一个 Tab。
    决策四：卡片主体进入详情页
    统一为：
    卡片主体 → 站内详情页
    访问官网 → 外部站点
    这样收藏、历史、SEO、统计才有完整入口。
    决策五：首页只展示精选内容
    不把 2400 条站点全部放到首页，而是：
    首页精选
    分类页完整数据
    Tab 做场景筛选
    搜索页做全量检索
